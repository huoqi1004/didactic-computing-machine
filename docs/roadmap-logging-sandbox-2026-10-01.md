## 1. 背景与目标

生产化路线图交付了治理面（RBAC→dry-run→分级审批→补偿→审计哈希链），定制化路线图交付了运行时可配置。但两条线完成后仍存在三个真实短板：

1. **日志不可查**：结构化日志只输出到 stdout，设计上"配合 Promtail 采集发送到 Loki"（`logging_config.py:15`），但 Loki/Promtail **从未部署**——容器重建即日志全失；出问题时无法回答"昨天 15 点谁做了什么"。
2. **链路不可串**：审计条目（audit_logs 表 10 列，`audit.py:362-373`）**没有 trace_id/business_key 列**——知道"发生了什么"，无法回答"这笔报销的对话→Agent 决策→工具执行→工作流→审计"是哪条链路；request_id 中间件只覆盖 HTTP 层（`logging_config.py:132-141`），Agent 工具链与工作流无 contextvar 贯穿（全仓 `bind_contextvars` 仅 logging_config.py 一处）。
3. **回滚不可运营**：写工具强制补偿（红线）已落地，补偿函数在失败时执行（`governor.py:201-208`）；但**没有统一的"操作回滚账本"**——审计知道"发生了什么"，没有结构化登记"如何撤销、是否已撤销"；工作流级 Saga 雏形完整（`event/saga.py`：execute/_compensate/persist/recover）但**未接入工作流 DSL**；代码执行沙箱只有注册守卫（`config.py:168-170`、`tools_v2.py:164-170`），容器隔离目录 `infra/sandbox/` 只有一份 README——**未落地**。

**目标（一句话，v1.1 修订）**：任何一次业务操作（无论来自页面、对话 Agent 还是工作流），管理员都能**仅凭业务单据号**在 5 分钟内还原完整链路（人证、参数、结果、审批、日志），且高风险写操作在 15 分钟内可按账本回滚（回滚前自动完成下游影响面检查）；本规划期结束时上述两项各通过一个 UAT 演练现场演示。

### 2.3 资源约束（方案选型的硬边界）

- 生产环境为腾讯云轻量 **2核2G/50G 盘**：Loki+Promtail+Grafana 全家桶常驻内存约 1G+，**不可行**；方案选型必须轻量自建或按需外置。
- 日志量估算：当前单实例 JSON 日志每日约 50~200MB（含 DEBUG），落库必须异步批量 + 分级采样，避免拖垮 MySQL；50G 盘对日志月增量有硬约束（见 §7 度量）。

## 3. 总体设计

### 3.1 追踪模型（v1.1 重写：三层键 + 业务键为第一入口）

**键层级定义（闭环 P1-1）**：

| 键 | 层级 | 生命周期 | 生成规则 |
|----|------|----------|----------|
| **business_key** | 根键（跨阶段稳定） | 单据全生命周期 | 业务单据号（报销单号/调拨单号/合同号/审批单号），由工具执行结果提取（result 已携带单据标识——补偿机制既有约定） |
| **trace_id** | 链路实例键 | 一次交互链路 | 入口层生成（HTTP 请求续传 `X-Trace-Id`，无则新建；Agent 会话/工作流 run 开始时若上下文无 trace 则新建）——一次业务横跨多个请求属**多条 trace**，靠 business_key 归组 |
| request_id | HTTP 层 | 单请求 | 现有中间件（复用） |
| thread_id / agent_run_id | 执行层 | 会话/工作流实例 | 现有（复用） |
| entry_id | 审计层 | 单审计条目 | 现有（复用） |

**关联规则**：business_key 与 trace_id **均可互查**——`operation_ledger` 以 business_key 为主查键（索引）、trace_id 为辅；`audit_logs` 新增 `trace_id` 与 `business_key` 两列（均带索引，旧数据 NULL 合法）。structlog contextvars 全链 bind trace_id；business_key 在工具执行产生单据时随审计/账本登记落列。

**W3C 兼容预留（裁决 D2 附加条件）**：trace_id 采用 32 位十六进制（与 W3C traceparent 的 trace-id 段同格式），将来切换 OpenTelemetry 时存量键无需迁移。

**还原动线（闭环 P0-1）**：管理员第一入口=**单据号搜索**（业务语言）→ 命中账本/审计条目 → 展开同链全部 trace（日志、审批单、工作流节点）。技术键 trace_id 作为二等入口保留在详情页。

### 3.2 回滚模型（账本 + 补偿复用，v1.1 强化）

```
operation_ledger（操作回滚账本，一次写操作一行）
  ledger_id / trace_id / business_key / actor / tool / domain
  forward_args(JSON) / forward_result(JSON)     ← 正向留痕
  compensation_ref                               ← 补偿函数指针（tools_v2 注册表已有）
  status: executed → compensating → compensated / compensate_failed
  rolled_by / rolled_at / rollback_approval_id   ← 回滚本身走治理面审批
  precheck_result(JSON)                          ← 回滚前置检查结果（闭环 P0-4）
```

#### 3.2.1 账本登记一致性（闭环 P0-2，方案论证）

委员会指出异步落账存在"执行成功→落账前崩溃"的幽灵操作窗口，给出两个方案。乙方论证如下：

- **方案 a（同事务）不可行**：治理面不持有业务事务——每个工具 handler 经 repository 自管 session（24+ 工具既有事务边界），强行同事务需重构全部工具的事务边界，回归风险与工期代价远超收益；且与既有架构原则冲突（审计与业务事务解耦，审计失败不阻塞业务）。
- **选方案 b（强化版）**：账本登记由"异步"改为**同步 `await` 单条 INSERT**（与治理面审计同模式，`governor.py:89` 先例；单条 INSERT 耗毫秒级，写操作本就是 DB 写路径，增量可忽略）——窗口从"无界异步队列"缩至"单条语句崩溃窗口"；再以**定时对账任务兜底**：审计链 `tool.*` 成功条目 ↔ 账本比对，审计有而账本无 → 自动补登记（标记 `backfilled=true`）+ P0 级告警。两层叠加后幽灵操作仅剩"INSERT 语句执行中进程被 kill"这一毫秒级窗口，且可被对账捕获并告警，满足红线 1 增补条款。

#### 3.2.2 补偿幂等门禁（闭环 P0-3）

三层防线：

1. **账本状态机 CAS 门禁**：回滚执行器发起补偿前原子推进 `executed → compensating`（单条 UPDATE 带状态条件），并发/重复回滚请求在门禁处直接拒绝——运营路径上补偿不会被重复调起；
2. **协议幂等强制**：`tools_v2` 补偿协议升级——补偿函数**必须以单据状态机为准实现幂等**（已回滚/已冲正则 no-op 并返回既有结果），`@erp_tool` 增加 `idempotent: bool` 声明字段，写工具注册时未声明幂等即拒绝（与"无补偿拒绝注册"同级红线）；
3. **drill 重放场景**：每个写工具的 drill 增加补偿重放断言（回滚成功后再次触发补偿 → 状态不变、返回 no-op），纳入 CI 门禁。

#### 3.2.3 回滚前置检查（闭环 P0-4）

按工具域注册 `rollback_precheck` 检查函数（登记表模式，与补偿指针同源管理）：回滚请求创建时执行，输出"下游引用清单"（该单据被哪些后续单据/流程引用）写入审批单 `precheck_result`。规则：**有下游引用 → 默认拒绝回滚**（审批单显式列出引用方），确需回滚走级联评估（人工列明级联补偿步骤后一并审批）。

## 5. 治理红线（v1.1：4 条 → 6 条，schema 锁死）

1. **账本不可删改、不可有幽灵**：operation_ledger 只允许状态机推进，禁止 DELETE/UPDATE 历史行；**审计链与账本定时对账，审计有而账本无的缺口必须自动补登记 + P0 告警**（闭环 P0-2）；回滚事件单独追加审计。
2. **回滚必审批、补偿必幂等**：任何回滚默认走治理面 write_high 人审（cio 快速通道同样留完整审批记录，驳回必填理由）；**补偿函数强制幂等声明**（已回滚则 no-op），重放经账本状态机 CAS 门禁（闭环 P0-3）。
3. **日志不可静默丢弃**：落库失败必须显式告警并降级重试，禁止吞异常。
4. **沙箱默认拒绝**：code-exec 类工具维持默认禁用；启用须同时满足容器隔离部署 + 显式开关 + 白名单三条件（延续 E2 原则）。
5. **审计者被审计**：日志查询、导出、账本查询等一切审计面操作行为自身 100% 落审计链（闭环 P1-3）。
6. **回滚先检查下游**：存在下游引用的单据默认拒绝回滚，级联回滚必须列明步骤并单独审批（闭环 P0-4）。
