# PRD 版本管理体系（Git 版本管理规范）

> 本目录存放 ERP 项目的 **PRD（产品需求文档）**及其评审资产。PRD 是需求的事实源——
> 一切功能迭代从 PRD 开始，经评审委员会批准后进入开发。

## 一、目录结构

```
docs/prd/
├── README.md                    # 本规范
├── CHANGELOG.md                 # 全部 PRD 的版本变更总账（追加不删改）
├── PRD-YYYY-MM-DD-<主题>-vX.Y.md # PRD 正文（一 PRD 一文件一版本线）
└── reviews/                     # 评审意见书（append-only，按 PRD 版本归档）
    └── PRD-...-vX.Y-review-YYYY-MM-DD.md
```

## 二、版本号语义

| 版本 | 含义 | 谁产生 |
|------|------|--------|
| v0.1~v0.n | 草稿迭代（乙方撰写/修订，甲方可随时批注） | 乙方 |
| v1.0 | 甲方评审通过（批准开发的定稿基线） | 评审通过时打 tag：`prd/<主题>/v1.0` |
| v1.1~v1.n | 批准后的小修订（澄清/补漏，不改范围） | 乙方修订 + 委员会确认 |
| v2.0 | 范围变更（新增/砍掉大功能） | 重新走评审 |

## 三、流程约定

1. **PRD 独立提交**：PRD 变更单独成 commit（不与代码混提），commit message 前缀 `docs(prd):`；
2. **版本快照**：v1.0 批准时打 git tag（`prd/<主题>/v1.0`），后续修订不改历史文件内容——新版本另存新文件，旧文件仅在头部标注 `superseded by ...`；
3. **评审留痕**：每轮评审意见书存 `reviews/`，PRD 头部维护"评审记录"表（日期/版本/结论/链接）；
4. **变更追踪**：开发实现必须引用 PRD 的 FR 编号（commit message 带 `FR-E1` 等）；
5. **批准即基线**：v1.0 是开发验收的需求基线——范围外变更必须走 v2.0。

## 四、PRD 正文统一结构

```
1. 背景与问题陈述（现状实测）
2. 目标 / 非目标
3. 用户与场景
4. 开源借鉴与采纳方式（逐项标注：引入框架 vs 借鉴思想自研）
5. 总体方案（架构 + 与治理面关系）
6. 功能需求（FR 编号，可验收）
7. 非功能需求（性能/安全/成本）
8. 里程碑与排期
9. 决策点（待甲方裁决）
10. 风险与开放问题
```
