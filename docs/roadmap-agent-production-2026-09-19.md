### 1.2 核心差距（为什么 Agent 还"不会干活"）

1. **LLM 只"说"不"做"**：`llm_chat`/`llm_analyze` 是纯文本进出的单发模式，没有工具调用循环——Agent 能生成"请补充 start_date/end_date"的引导话术，但无法真正调用 `get_reimbursements()` 把数据查出来（2026-09-19 实测复现）。
2. **无编排**：没有状态图/工作流执行引擎把"理解意图 → 调工具 → 综合结果 → 需要时请人审批 → 继续"串起来；工作流引擎与 Agent 互不相通。
3. **工具层是空壳**：tool_registry 无参数 schema、无调用审计、无风险分级执行策略、无幂等/回滚语义，且与 LangChain 工具格式不兼容。
4. **人审有配置无机制**：决策标记 `requires_human_approval` 后，没有任何暂停-等待-恢复的执行路径。
5. **无沙箱与回滚**：工具直接执行真实写操作，失败无法补偿，高危操作无隔离。

## 2. 总体策略

**先立骨架、再长肌肉、后上保险。** 不做"33 个 Agent 一次性重写"——以 **AgentRuntime 集成层**（LangGraph 图模板 + 工具协议 v2）为唯一新骨架，用**双试点场景（报销助手 + 资金管家）证明闭环**，再按"查询类 → 操作类 → 跨域流程类"三批推广；**MCP 标准化后置**（审批定稿：先用本地工具跑通全部场景与协同，再做 MCP 化收尾——工具协议 v2 的"注册即导出"设计保证后切无返工），Agent 大规模可用的时点因此提前约 2.5 周。

三条设计红线（贯穿所有阶段）：
1. **一切工具调用必经治理面**：RBAC 权限校验 + 参数 schema 校验 + 风险分级 + 审计哈希链 + 限流，绕过治理面的调用路径不允许存在；
2. **写操作分risk分级管控**：所有写操作执行前强制 dry-run 预演留痕；`write_low` 免审批（事后抽样审计），`write_high`（资金/薪酬/合同/删除类）必须经 `interrupt()` 人审门（决策 D6）；
3. **可回滚才可执行**：所有写工具注册时必须提供补偿函数（幂等），纳入 Saga 编排，否则只能以只读工具身份存在。

**关键技术选型（已审批确认，见 §10）**：
- 人审采用 LangGraph 现行 `interrupt()` + `Command(resume=...)` 模式（旧的 `interrupt_before` 编译参数已过时）；
- **Checkpointer：自研 MySQL Checkpointer**（`BaseCheckpointSaver` 实现，状态 JSON 序列化入 MySQL 表）——零新增运维组件，守住"一条命令部署"底线；
- MCP：`langchain-mcp-adapters` 独立库已于 2026-09-17 归档，采用 LangChain 官方 **`MCPAdapter`（基于 FastMCP）**；内部 MCP Server 用 FastMCP 构建，传输为 **streamable HTTP + 令牌鉴权**；
- LLM 治理：**复用现有 LLM 客户端**（冷却/熔断/降级）+ 治理面计量与预算限流；LiteLLM 网关推迟到 Phase E 评估；
- 追踪评估：**OpenTelemetry 自建优先**（数据不出域，复用已接入 otel），LangSmith 不启用；评测体系以评测集 + CI 门禁自建。

## 4. 人审与操作回滚设计（核心机制专节）

### 4.1 人在环（Human-in-the-Loop）真正跑通

```
用户指令(Messaging/页面)
  → LangGraph 图启动（thread_id=业务单据号，状态入 MySQL Checkpointer）
  → Agent 推理节点（LLM 决定调用哪些工具）
  → 治理面校验（RBAC/schema/风控）
  → dry-run 预演（所有写操作强制，影响预览入审计）
  → [write_high] → interrupt() 暂停，图状态持久化
        → 生成审批任务（写入 workflow_requests 表 + 推送审批中心/Messaging 卡片）
        → 审批人批准/驳回（审批中心或聊天里点按钮）
        → Command(resume=批准结果) 恢复图执行（超时未审 → auto_fallback_to_human 策略）
  → 工具执行节点（Saga 包裹，失败自动补偿）
  → 结果综合节点 → 回复用户 + 全程审计
```

- **分级审批策略（决策 D6）**：`write_low`（如报销草稿提交、备注修改）免审批直接执行，事后按抽样率审计复查；`write_high`（资金调拨、薪酬变动、合同签署、删除类）100% 强制人审。风险级在工具注册时声明，调整需治理评审；
- **断点恢复不惧重启**：人审等待中后端重启，MySQL Checkpointer 里图状态仍在，审批后可继续执行（生产级与玩具的分水岭）；
- **审批超时**：复用 `human_approval_timeout`，超时自动升级或转人工处理（策略可配）；
- **审批入口**：审批中心页面 + Messaging 内嵌审批卡片（批准/驳回/改参三个动作，卡片上展示 dry-run 预演结果）。

### 4.2 操作回滚（沙箱语义在 ERP 场景的落地）

"沙箱"在本项目拆成两个正交机制：

| 机制 | 针对对象 | 实现 |
|------|---------|------|
| **执行沙箱**（隔离） | 代码执行类工具（数据分析/报表计算等任意代码） | Docker 容器隔离：`--network none` + 只读文件系统 + 非 root + 内存/CPU 限额 + 墙钟超时 + 输出白名单回传。**初期默认禁用此类工具**，数据计算一律走预注册的安全函数（Phase E 按需开启） |
| **效果沙箱**（可撤销） | 全部写操作工具 | 三层：① **dry-run 模式**——工具声明 `supports_dry_run`，写操作执行前强制预演，结果进人审卡片与审计；② **Saga 补偿**——写工具注册时必须提供幂等补偿函数（如 `create_order` 配 `cancel_order`），执行失败/人工回滚时由 SagaCoordinator 按逆序补偿；③ **事务边界**——单工具内 DB 写走事务，跨工具流程由 Saga 保证最终一致 |

回滚本身也是受治理的操作：回滚动作全量审计（哈希链）、`write_high` 单据的回滚同样要过人审门、回滚演练是操作类工具的**准入测试**（见 Phase E 验收）。

## 5. 分阶段路线图（定稿顺序：MCP 后置）

> 依据决策 D7：先以本地工具形态跑通全部场景与多 Agent 协同（M-A→M-C，Agent 大规模干活提前约 2.5 周到来），再做 MCP 标准化收尾（M-D），最后沙箱加固（M-E）。

### Phase A：编排基座与双场景闭环（4 人周）

**目标**：LangGraph 跑起来，治理面立起来，用**报销助手 + 资金管家双场景**证明"Agent 能查、能报、能请人审批、重启可恢复"（决策 D5）。

**退出标准（全部可验证）**：
1. **报销场景**：在 Messaging 里对报销助手说"查一下上个月的报销单"，Agent **真实调用工具**返回 DB 中的报销列表（不再是引导话术）；说"帮我提交一笔 800 元的办公费报销"，组装表单 → dry-run 预演 →（write_low 免审直接提交 或 按配置走人审）→ 落库成功；
2. **资金场景**：对资金管家说"看下今天的资金日报/支付排程"，真实返回数据；说"申请一笔 80 万的资金调拨"，触发 `interrupt()` 人审 → 审批中心出现待审卡片（含预演）→ 批准后**后端重启一次**仍能恢复执行 → 调拨落库、余额变动正确；
3. **人审分级生效**：同一条指令对 write_low 与 write_high 工具分别走免审与强制人审两条路径；
4. 治理面生效：无对应权限的用户指令调用工具被拒（403 语义），每次工具调用在 `audit_logs` 有记录且哈希链连续；
5. MySQL Checkpointer 单测 + 断点恢复集成测试通过。

### Phase B：编排闭环批量推广（3.5 人周，本地工具形态）

**目标**：三批场景迁移，覆盖全部高价值 Agent；操作类工具全部带 dry-run、分级审批与回滚能力。

**退出标准**：
1. **查询类（12+ 工具）**：payroll/hr/crm/sales/treasury/contract/invoice/tax 等的只读查询全部可被 Agent 真实调用，答案与 API 直查一致（对比测试）；
2. **操作类（8+ 工具）**：销售下单、合同创建/审批建议、薪酬计算提交、报销审批动作、资金调拨审批动作等，100% 走"dry-run 预演 → 分级审批 → 执行 → 可补偿"，审批拒绝/超时策略生效；
3. **跨域工作流图（3 条）**：报销审批流（员工→AI 预审→人审→付款）、采购到支付（PO 审批→支付排程→凭证）、合同审批流，全程 Checkpointer 持久化、可中断恢复、每步审计；
4. 回归保护：现有 1000+ 测试不回归；新增场景端到端测试全绿；
5. LLM 成本：单次指令 token 消耗计量入审计（治理面计量），超预算指令被限流。

### Phase C：多 Agent 协同（2.5 人周）

**目标**：Supervisor 模式跑通跨域任务，事件驱动协同与图编排融合。

**退出标准**：
1. Supervisor 图上线：跨域指令（如"把上个月北京大区的报销和差旅数据汇总给我"）被正确路由到 reimbursement+travel 子 Agent 并综合答复；
2. "采购到支付"跨 Agent 流程：采购 Agent 与资金/会计 Agent 通过 supervisor 编排 + 事件总线协作完成，任一环节人审可介入；
3. Agent 间调用全部经治理面（无 Agent 直连另一个 Agent 内部方法的后门）；协同过程可在 otel 追踪里看到完整跨 Agent 链路；
4. 失败传播可控：子 Agent 失败 → supervisor 降级/换 Agent/报告用户，不无限重试（复用熔断）。

### Phase D：MCP 化与技能标准化（2.5 人周，收尾阶段）

**目标**：把已跑通的工具体系标准化为 MCP 形态（对外/跨系统可消费），Skill 让"能力组合"可复用、可管理。**因工具协议 v2 预留了导出接口（A2），本阶段无返工，为已注册 20+ 工具一次性开启 MCP 形态。**

**退出标准**：
1. 5 个域 MCP Server（finance/hr/sales/contract/treasury）以 streamable HTTP + 令牌鉴权运行，LangGraph 经官方 MCPAdapter 调用与本地调用**行为一致**（同一测试双跑断言）；
2. 外部 MCP 工具接入走配置清单（白名单 + 治理面强制过桥），demo 接入 1 个外部工具（如汇率）；
3. 首批 6 个 Skill 上线并在编排中使用（skill=提示模板+工具白名单+护栏档案，热加载）；
4. 工具目录 API（列出全部工具/技能/权限要求/风险级/调用统计）供管理页消费。

### Phase E：沙箱、回滚演练与生产加固（2.5 人周）

**目标**：把"安全"从设计变成可演练的事实；建立持续防回归的评测与成本护栏。

**退出标准**：
1. **回滚演练通过**：对全部 write 类工具注入故障（执行后崩溃/部分失败/补偿失败），Saga 补偿成功率 100%，数据一致性校验通过；演练脚本固化为 CI 用例（脚本在 Phase B2 已随工具产出）；
2. `write_high` 操作人审拦截率 100%（审计抽样验证）；审批超时策略生效（超时转人工）；write_low 抽样审计机制运行；
3. 代码执行沙箱（若启用）：容器隔离验证（无网络/只读/限额/超时击杀），默认关闭状态下有开关文档；
4. 评测集扩到 50+ 用例并接入 CI，提示词/模型变更跑评测门禁；
5. 成本护栏：per-agent 日预算、超限降级到规则路径（复用冷却机制），报表可见；**同期产出 LiteLLM 网关评估结论（决策 D3 约定）**；
6. 压测：50 并发指令下编排稳定（无死锁/泄漏），Checkpointer 读写无瓶颈；
7. 全链路安全审计：工具越权 0、审计链连续、DID 贯穿（人/Agent/工具三级主体）。

## 7. 风险与回滚

| 风险 | 应对 |
|------|------|
| LangGraph 版本迭代快、API 变动 | 锁定版本；A5 集成层做薄抽象（graph 模板与 LangGraph 解耦的防腐层），升级只动适配层 |
| 自研 MySQL Checkpointer 出隐性 bug（状态损坏） | 状态 JSON 带版本号与校验和；人审等待中的图可降级为"人工重建上下文继续"；保留导出/重放工具 |
| MCP 后置导致 Phase B/C 工具形态与后续 MCP 化不一致 | 工具协议 v2（A2）即按"注册即导出"设计，MCP 仅是传输形态切换；M-D 双跑一致性断言兜底 |
| 工具治理面成为性能瓶颈 | 治理面纯进程内（无远程调用），RBAC 走内存缓存；压测验证（E5） |
| LLM 输出幻觉调用不存在的工具 | schema 校验强制拒绝 + 评测集回归 + 工具描述质量评审 |
| 人审成为瓶颈拖慢业务 | 分级免审（D6：write_low 免审+抽样审计）；审批超时自动策略 |
| 操作类工具补偿逻辑写错造成二次损坏 | 补偿函数单测 + 回滚演练准入（E1）+ 高危回滚本身需人审 |
| 33 个 Agent 范围蔓延 | B5 只暴露查询接口不迁持久化；编排按场景推进，不为凑数全量改造 |
| 与 9/3 路线图 Phase 3 剩余项（RAG/前端对齐/迁移）冲突 | 本路线图优先；RAG（3.3）与前端对齐（3.5）排在 M-E 之后另立计划，两者共享本路线图的治理面与编排层 |

## 9. 明确不做（范围控制）
