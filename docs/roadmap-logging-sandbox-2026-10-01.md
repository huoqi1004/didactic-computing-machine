# 可观测与沙箱回滚路线图 —— 日志系统 + Agent/工作流溯源回滚

- **文档版本**：v1.0（待甲方评审委员会评审）
- **制定日期**：2026-10-01
- **前序路线图**：生产化路线图（A~E 已交付，60d9938）、定制化平台路线图（F1~F5 已交付，8614005/7e021ac）
- **本规划期主题**：① 搭建项目级日志系统——操作全量记录、全链路可追溯；② 为各 Agent 与工作流配置沙箱——所有操作可溯源、可回滚
- **诚实原则**：现状基线每条均经代码核对（附 `文件:行号`），凡未落地的一律写「未落地」，不粉饰

## 1. 背景与目标

生产化路线图交付了治理面（RBAC→dry-run→分级审批→补偿→审计哈希链），定制化路线图交付了运行时可配置。但两条线完成后仍存在三个真实短板：

1. **日志不可查**：结构化日志只输出到 stdout，设计上"配合 Promtail 采集发送到 Loki"（`logging_config.py:15`），但 Loki/Promtail **从未部署**——容器重建即日志全失；出问题时无法回答"昨天 15 点谁做了什么"。
2. **链路不可串**：审计条目（audit_logs 表 10 列，`audit.py:362-373`）**没有 trace_id/thread_id 列**——知道"发生了什么"，无法回答"这笔报销的对话→Agent 决策→工具执行→工作流→审计"是哪条链路；request_id 中间件只覆盖 HTTP 层（`logging_config.py:132-141`），Agent 工具链与工作流无 contextvar 贯穿（全仓 `bind_contextvars` 仅 logging_config.py 一处）。
3. **回滚不可运营**：写工具强制补偿（红线）已落地，补偿函数在失败时执行（`governor.py:201-208`）；但**没有统一的"操作回滚账本"**——审计知道"发生了什么"，没有结构化登记"如何撤销、是否已撤销"；工作流级 Saga 雏形完整（`event/saga.py`：execute/_compensate/persist/recover）但**未接入工作流 DSL**；代码执行沙箱只有注册守卫（`config.py:168-170`、`tools_v2.py:164-170`），容器隔离目录 `infra/sandbox/` 只有一份 README——**未落地**。

**目标（一句话）**：任何一次业务操作（无论来自页面、对话 Agent 还是工作流），都能用同一个追踪键在 5 分钟内还原完整链路（人证、参数、结果、审批、日志），且高风险写操作在 15 分钟内可按账本回滚；本规划期结束时上述两项各通过一个 UAT 演练现场演示。

### 2.3 资源约束（方案选型的硬边界）

- 生产环境为腾讯云轻量 **2核2G**（`.workbuddy/memory/2026-09-04.md`）：Loki+Promtail+Grafana 全家桶常驻内存约 1G+，**不可行**；方案选型必须轻量自建或按需外置。

## 3. 总体设计

### 3.1 追踪模型（一个键串全程）

```
trace_id（每次用户请求/Agent 会话触发生成，UUID 短码）
  ├─ request_id        HTTP 层（已有，复用）
  ├─ conversation_id   对话/消息层（已有消息表）
  ├─ thread_id         工作流/LangGraph 层（已有 checkpoints）
  ├─ agent_run_id      Agent 执行层（治理面 ctx 已有 run 概念）
  └─ entry_id          审计层（新增 trace_id 列反向关联）
```

统一原则：**列新增、不改旧语义**——audit_logs 加 `trace_id` 索引列（旧数据回填 NULL 合法），structlog contextvars 在治理面入口与工作流 DSL 节点边界 bind/unbind，所有日志行自动携带。

### 3.2 回滚模型（账本 + 补偿复用）

```
operation_ledger（操作回滚账本，一次写操作一行）
  ledger_id / trace_id / actor / tool / domain
  forward_args(JSON) / forward_result(JSON)     ← 正向留痕
  compensation_ref                               ← 补偿函数指针（tools_v2 注册表已有）
  status: executed → compensating → compensated / compensate_failed
  rolled_by / rolled_at / rollback_approval_id   ← 回滚本身走治理面审批
```

原则：**补偿函数不重写**——账本只是把"已注册的补偿"变成"可查询、可审批、可运营的撤销指令"；governor 执行成功即落账本（异步，不阻塞主链路）。

### 3.3 沙箱模型（分级，按需落地）

| 级别 | 对象 | 机制 | 本期范围 |
|------|------|------|----------|
| S1 参数沙箱 | 全部写工具 | dry-run + schema 校验（已有） | 保持 |
| S2 影子执行 | 高风险写工具 | 执行前快照受影响单据 + 影响面报告进审批单 | 新建 |
| S3 事务沙箱 | 工作流 | Saga 逆序补偿 + Checkpointer 状态恢复 | 新建（接 DSL） |
| S4 代码沙箱 | code-exec 工具 | 受限容器（无网络/只读根/资源限额/一次性） | 决策点 D5 |

## 5. 治理红线（schema 锁死，与前期红线同级）

1. **账本不可删改**：operation_ledger 只允许状态机推进，禁止 DELETE/UPDATE 历史行；回滚事件单独追加审计。
2. **回滚必审批**：任何回滚默认走治理面 write_high 人审；回滚操作本身 100% 审计（谁、何时、回滚了哪笔、结果）。
3. **日志不可静默丢弃**：落库失败必须显式告警并降级重试，禁止吞异常。
4. **沙箱默认拒绝**：code-exec 类工具维持默认禁用；启用须同时满足容器隔离部署 + 显式开关 + 白名单三条件（延续 E2 原则）。

## 6. 风险与对策

| 风险 | 对策 |
|------|------|
| 2核2G 上日志落库拖垮 MySQL | 异步批量 + 队列上限熔断 + DEBUG 级不落库；性能门禁 G6.1 |

## 8. 决策点（请评审委员会逐项裁决）

| # | 决策点 | 选项 A | 选项 B | 乙方建议 |
|---|--------|--------|--------|----------|

| D4 | 回滚审批策略 | 全部回滚 write_high 人审 | 高频小额免审 + 大额人审 | **A**。回滚是比正向操作更敏感的动作（可能掩盖舞弊），一律人审；紧急场景以"cio 快速审批通道"实现（仍是审批，只是提醒升级） |
| D5 | 代码执行沙箱 | 本期真落地：受限容器（无网络/只读根/资源限额/一次性）+ code-exec 白名单工具 | 维持禁用，出书面评估关闭，待有真实代码执行需求再立项 | **B**。当前系统**没有任何已注册的 code-exec 工具**（守卫至今拦截为零工具），为不存在的需求建容器是负 ROI；但 G5.4 交付评估报告而非直接关闭，若甲方预见数据分析/报表代码执行需求请选 A |
| D6 | LLM 交互日志 | 默认记摘要（参数脱敏摘要+token），全文按域开关 | 全文落库（排查强但体积/敏感面大） | **A**。全文含业务敏感与提示词资产，默认摘要；确需排查时按域临时开全窗 |
