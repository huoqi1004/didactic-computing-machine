## 1. 一分钟认知：三套记录、各管一件事

| 层 | 载体 | 回答的问题 | 可否篡改 |
|----|------|------------|----------|
| 审计哈希链 | `audit_logs`（365 天） | "谁在何时对什么做了什么"（防篡改证据） | 改动即断链暴露 |
| 操作日志 | `operation_logs`（热 30 天→归档 180 天） | "把相关的记录都找出来给我看"（查询层） | 可查询、可导出 |
| 回滚账本 | `operation_ledger` | "这步操作怎么撤销、撤销到哪一步了" | 只能状态机推进 |

三者经**同一追踪键**互相关联：业务单据号（business_key，第一入口）+
链路键 trace_id（32 位十六进制，二等入口）。

## 2. 操作日志查询（管理台 → /cio-admin →「操作日志」）

**第一入口永远是单据号**：在顶部"业务单据号"框输入报销单号/调拨单号/合同号，
点查询——命中该单据的全部操作（Agent 决策、工具执行、审批、补偿）一次拉出。

- 过滤器：操作人/动作前缀（如 `tool.`、`rollback.`）/来源/风险/结果；
- **同链视图**：任一行点「同链」或详情抽屉内「查看同链全部操作」——按该行
  trace_id 过滤，还原一次交互链路的完整时序（UAT-G1-1 的动线）；
- 详情抽屉：完整 details JSON（LLM 交互默认只记摘要，全文模式见 §6）；
- 导出 CSV：右上「导出 CSV」（需 `operationlog:export`；**谁导出了什么，
  这件事本身会进审计链**——含过滤条件与行数）；
- 命中标注"（命中归档表）"：该记录已过 30 天热留存，从归档表返回
  （链路还原不受留存分层影响）。

## 3. 误操作回滚（四步，全程有审批）

1. **找到账本行**：「操作日志」页搜单据号 → 详情拿 ledger 行；
   或 API `GET /api/v1/agent-ops/operation-rollback/ledger?business_key=<单据号>`；
2. **发起回滚**：`POST .../operation-rollback/{ledger_id}/request`，body 填 `reason`
   （理由进审批单与审计，必填意识上别留空）——系统自动跑**回滚前置检查**：
   存在下游引用时**直接拒绝**并返回引用清单（这是红线保护，不是故障）；
3. **审批**：回滚一律 write_high 人审（审批中心出现 `rollback:{ledger_id}` 卡片，
   含正向参数/理由/前置检查结论）；批准人=第二双眼睛（D4 裁决：cio 发起也须审批）；
4. **执行与确认**：批准后自动执行补偿；账本行状态机
   `executed → compensating → compensated`（或 `compensate_failed`）。
   失败时 error 级告警送达（含 ledger_id 与排查指引）——修复后**重新发起**即可重放，
   已成功的回滚**不可重放**（状态机门禁拒绝）。

**什么时候该回滚而不是改数据**：只要是业务单据（有账本行），一律走回滚通道——
直接改库会绕过审计链与账本状态机，属于内控违规。

## 4. 审计链完整性校验（防篡改）

- **例行**：调度循环每小时自检（增量每日、全量每周），结果落在
  `audit_verify_state.last_report`；
- **手动即时校验**：「操作日志」页顶部完整性卡片 →「立即全量校验」
  （`POST .../operation-logs/verify/run`，需 `audit_verify:run`）——
  30 秒内返回：`ok`（checked=N 条完整）或 `broken`（broken_at 点名被篡改条目 +
  expected/actual 哈希并列）+ critical 告警；
- 看到断链 = 发生安全事件：立即走事件响应（保全库快照、核对 broken_at 之后的
  全部条目），**不要**手工修数据（修复过程也要留痕）。

## 5. 告警处理（谁在什么时候该被叫醒）

| 告警规则 | 级别 | 含义 | 首要动作 |
|----------|------|------|----------|
| `audit_chain_broken` | critical | 审计哈希链断链（篡改/库损坏） | 事件响应流程 |
| `ledger_ghost_operation` | error | 审计有而账本无（登记窗口丢失） | 对账已自动补登记；排查该时间窗是否崩溃 |
| `rollback_compensation_failed` | error | 回滚补偿失败 | 按 runbook 剧本三人工介入后重放 |
| `workflow_saga_needs_manual` | error | 工作流失败补偿需业务决定（如资金已动） | 业务负责人决定后续（可能走回滚账本） |
| `high_freq_permission_denied` | warning | 同一用户 5 分钟 ≥10 次越权 | 核实账号是否被盗用/误配权限 |
| `off_hours_write` | warning | 22:00~06:00 写操作 | 核实操作人是否有正当理由 |
| `audit_db_failure` / `oplog_flush_failure` | warning | 审计/日志落库失败（内存降级） | 查 MySQL；恢复后自动续写 |

**告警通道**：事件进消息中心；配置 `ERP_ALERT_WEBHOOK_URL` 后同步推送到
飞书/钉钉/企微机器人（推送失败有死信表兜底，恢复后自动/手动补推）。

## 6. LLM 交互日志全文开关（默认关）

- 默认只记摘要（域/token/消息数）——提示词与回复**全文不落库**；
- 临时排查需要全文：定制中心 → `agent:observability` 域参数
  `llm_fulltext_logging` 申请开启（**放宽类变更自动转人审**——批准人即
  第二确认人）；≤7 天自动过期（含已落库全文，凭 expires_at 提前清理）；
- 排查结束建议手动关闭（同样走审批，双人在场留痕）。

## 7. 与操作日志相关的两个"不要"

1. **不要手工 DELETE operation_ledger**——红线 1：账本只能被状态机推进；
   需要清理的是 operation_logs（系统按 30/180 天自动分层，无需人工）；
2. **不要绕过查询 API 直接连库出报表**——导出行为自身要审计（红线 5：
   审计者被审计），库内直查会让"谁看了什么"失去记录。
