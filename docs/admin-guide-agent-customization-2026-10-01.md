## 1. 一分钟认知：改配置不是改代码

三层：**内置默认（代码）→ 定制覆盖（管理端配置，存 MySQL）→ 运行时合成**。

- 你在管理端做的每一次定制，**不需要发版**；生效后约 5 秒内多实例收敛（实测 0.36~5.25 秒）。
- 收紧类变更（更安全、更多审批、更低限额）**即时生效**。
- 放宽类变更（**红线**）**自动转人审**，未批不生效；变更全过程写 `customization_versions` + 审计哈希链，不可删。
- 任何时候都能回滚到任意历史版本或出厂默认。

## 2. 谁能动：实测权限矩阵（以代码为准，非路线图承诺）

进入管理台的门槛是路由守卫 `resource="system" action="manage"`（`frontend/src/App.tsx:155`）。

| 角色 | 能进 /cio-admin | customization 动作 | agent:read / agent:approve | 现实结论 |
|------|----------------|--------------------|---------------------------|----------|
| `cio` | ✓（`system: _ALL`） | read,update,approve,create,publish,export（`seed.py:793`） | ✓（`agent: _ALL`） | **主力操作角色**（种子账号 `admin` 实为 cio，`seed.py:875-881`） |
| `ceo` | ✓（`system: _ALL`） | read,create,update,approve（由 `seed.py:448` 兜底通配获得，无 publish/export） | ✓ | 可操作、可审批，**不能发布** |
| `chairman` | ✗（仅 `system: _R`） | read,approve,create,publish（`seed.py:795`） | ✗ | 进不了台，publish 拿不到用 |
| `customization_admin` | ✗ **没有 system:manage** | 全部 8 个动作（`seed.py:789`） | ✗ | **当前无法在 UI 操作**（见 §2.1） |
| `customization_approver` | ✗ **没有 system:manage** | read,approve,publish（`seed.py:790`） | ✗ | **当前无法审批**（见 §2.1） |

### 2.1 已知阻塞：两个专用角色进不了台（务必读）

`customization_admin` / `customization_approver` 在 `ROLE_PERMISSION_MATRIX` 里**只被授予 `customization` 一个资源**
（`seed.py:789-790`，全仓 grep 这两个角色名 + `system`/`agent` = 0 命中），而：

- 进 /cio-admin 需要 `system:manage`（`App.tsx:155`）→ 直接被路由守卫挡在门外；
- 定制中心顶部的「批准/驳回」按钮门是 `agent:approve`（`AgentCustomizationCenter.tsx:261`，
  无权限时显示「需 agent:approve 权限」）；
- 待审批列表来自 `GET /agent-ops/approvals`，需要 `agent:read`。

**过渡动线（现阶段唯一可用）**：由 `cio`（或 `ceo` 做审批）执行定制操作。
把两个专用角色接上 `system:manage` + `agent:read` + `agent:approve` 属于**权限授予（安全边界）变更**，
已列入待决策 D5，需甲方确认后再改种子，手册不假装它已经能用。

另有一处**必须知道的实现细节**：界面上的批准/驳回**不是**调用
`POST /api/v1/agent-ops/customizations/{ctype}/{target}/decide`（该端点存在且要求 `customization:approve`，
但 `frontend/src/services/api.ts` 中**无调用方**），而是调用
`POST /api/v1/agent-ops/approvals/{thread_id}/decide`（`api.ts:2006-2008`），
由它按 `thread_id` 走 `apply_pending` 使定制生效（组件注释 `AgentCustomizationCenter.tsx:12`）。
→ 所以**审批人真正需要的是 `agent:approve`**，只给 `customization:approve` 不够。

### 4.1.1 风控阈值：能改什么、改了会怎样

当前注册表三把线（真机 `/meta` 实测回显，出厂值即代码里的 `THRESHOLD_DEFAULTS`）：

| 键 | 界面显示名 | 出厂默认 |
|----|-----------|---------|
| `reimbursement_auto_approve_limit` | 报销免审线（元） | 5000 |
| `payment_human_gate_limit` | 大额付款人审线（元） | 100000 |
| `agent_daily_token_budget` | 单 Agent 日 token 预算 | 2000000 |

三条必须讲清的规则（红线 2 的运行期口径，F5.6 整改后）：

1. **上调 = 放宽 = 转人审**。把免审线从 5000 调到 8000，界面会先提示
   「放宽类变更，需人工审批后生效」，保存后返回 `pending_approval`，
   **批准前工作流仍按 5000 跑**（真机实测：生效层不出现该 gate 条目）。
2. **下调 = 收紧 = 即时生效**，保存即参与运行（5 秒内多实例收敛）。
3. **停用一份比出厂线更紧的覆盖，方向是放宽**：例如把免审线覆盖 1200 停用，
   生效值会升回出厂 5000，系统同样转人审。想立刻放松，只能走审批；想立刻收紧，直接调小。

白名单外的键（打错的、或历史遗留的）**后端直接 400 拒绝**，不会写进生效层——
这条是防「界面显示已覆盖、运行期没人读」的死键。阈值 `value` 必须是**非负数字**，
填文字、负数同样 400。

### 4.2 工作流设计（`WorkflowDesigner.tsx`）

校验 `:845`（无门）→ 保存草稿 `:847`（`customization:update`）→ 申请发布 `:853`（`customization:publish`）→
载入编辑 `:886`（无门）→ 回滚 `:891`（`customization:publish`）。
另可直接加条件分支节点 / 删节点（D-2 多路路由；运行期按单据 ID 哈希做粘性灰度 S1）。

**发布前一定先点「校验」**：DSL 校验器会拦条件分支缺省路、孤立节点等；校验通过才会落草稿。

条件分支（D-2）的两条硬规则，报错文案里会直接点名：`condition` 节点**必须有 `default`**（失败安全，
全不命中时走它），每个分支的算子只能写一个、且必须是全名
`equals/not_equals/in/gt/gte/lt/lte/exists`（写成 `eq` 会被拒）。
真机实测（2026-10-01，`procure_to_pay`）：故意删掉 `default` 后点「保存草稿」，
**后端仍然 400** 并把同一串可读原因回显成
`DSL 校验未通过：condition 节点 triage 缺少 default（失败安全）`，草稿表零写入——
所以「先校验」是给你省时间，不是系统唯一的闸口（不靠前端自觉）。

### 4.3 MCP 治理（`McpGovernance.tsx`）

登记 Server `:225` → 测试连接 `:337` → 勾选要暴露的工具 `:405` → 开/关出口域 `:510`。全部 `customization:update`。

- 地址有**三道 SSRF 关卡**：协议只允许 http/https、禁止内网段与元数据地址、禁止 IP 直连（域名解析后二次校验）；
  生产另叠加出站域名白名单（白名单优先于解析校验，见 §复审备注 3）。
- **「新外部 MCP 接入」按红线算放宽**，必然转人审——不要在登记成功后以为外部工具已经可用，
  要去待审批区确认它被批准。
- 删除 `:337` 同块；删除只撤配置，历史审计保留。

### 4.6 评测趋势（`EvalTrendBoard.tsx`）

## 5. 常见报错 → 原因 → 你该做什么

| 现象 | 原因 | 处置 |
|------|------|------|
| 点了 /cio-admin 链接却跳回首页 | 你的角色没有 `system:manage` | 用 cio 账号；见 §2.1 |
| 待审批区显示「需 agent:approve 权限」 | 只有 `customization:approve`，没有 `agent:approve` | 审批要走 agent 权限（§2.1） |
| 保存定制后 Agent 行为没变 | 该变更是**放宽类**，还在等人审 | 到待审批区看是否 pending；未批不生效是失败安全 |
| 改阈值后提示「已提交人工审批」而不是「已生效」 | 你**上调**了线（放宽），或停用了一份比出厂线更紧的覆盖 | 到待审批区请 `agent:approve` 的人批准；要立刻生效只能往紧的方向调 |
| 保存阈值时 HTTP 400「未知的 gate 配置项」 | 有人绕过界面直调 API 写了注册表外的键（那种键运行期没人读） | 只在「风控阈值」分区里操作，清单由后端下发 |
| 保存阈值时 HTTP 400「overrides.value 须为非负数字」 | 值填成文字、负数或字符串数字 | 填数字；界面已拦，API 侧同样拦 |
| 保存时 HTTP 500「内部服务器错误」 | 定制层此刻不可写（MySQL 故障），**这是保护** | 停止重试，通知运维按运维手册 §4.2 处置 |
| HTTP 429 | 两道限流之一：IP 层（写 60/min、全局 120/min）或租户配额（basic 60 / standard 600 / enterprise 3000 per min） | 降频或让运维核对租户档位 |
| 管理端改了权限但界面不更新 | 前端 authStore 不在页面加载时重新拉 `/auth/me` | 退出重登（或刷新后重新登录） |
| 界面显示降级但业务正常跑 | 定制层读不到，正在按内置默认或旧缓存运行 | 看 `/api/v1/agent-ops/customizations/degradation` 的 `mode`，按运维手册 §3、§4.1 判型 |

## 7. 考核卷（12 题，合格线 10 题）

1. 管理端改定制需要发版吗？生效要多久？
2. 「把审批金额上限从 5000 提到 50000」会即时生效吗？为什么？
3. 待审批的放宽变更在批准前，运行时用的是新值还是旧值？
4. 谁能在界面上点「批准」——只有 `customization:approve` 够吗？
5. 停用一项定制后，生效视图里还能看到它吗？运行时还采纳吗？
6. `mode=defaults` 和 `mode=stale_cache` 分别意味着什么？哪个更危险？
7. 定制层读库失败时，`/api/v1/health` 会挂吗？该先查哪三个地方？
8. 保存定制返回 500，最可能的原因是什么？该重试吗？
9. 回滚有哪两种粒度？分别在哪里操作？
10. `customization_versions` 和审计链能删吗？为什么？
11. 发布工作流前必须点哪个按钮？资金域评测低分会怎样？
12. 接入一个新外部 MCP Server 需要注意哪两条硬约束？

**答案要点**：
1 不需要；约 5 秒内多实例收敛（实测 0.36~5.25s）。
2 不会——放宽类自动转人审，未批不生效。
3 旧值（当前生效覆盖），提案只落在 `customization_versions` 的 pending 行。
4 不够；界面门是 `agent:approve`，审批实际调用 `/agent-ops/approvals/{thread_id}/decide`（§2.1）。
5 看得到（显示为已停用），运行时不再采纳。
6 defaults=从没读到过、按代码出厂值跑（所有自定义都不生效）；stale_cache=在吃最后一次成功的旧值（可能与库里已发布的不一致）。defaults 更危险，因为它意味着「你以为改过的东西一条都没生效」。
7 不会挂（实测 200）；查 `/degradation` 的 `mode`、`erp_customization_degraded` gauge、`customization.degraded` 日志（注意每事故只 1 条）。
8 定制层不可写（MySQL 故障），是保护审计完整性的失败安全；**不要反复重试**，通知运维。
9 单项回滚（定制中心/工作流/技能分区的「回滚」或 `POST .../{ctype}/{target}/rollback`）与整体回出厂（清生效表，CI 已守护）。
10 不能——红线 3 要求变更 100% 可追溯，删了就无法举证谁在何时改了什么。
11 「校验」；D-4 强制阻断发布。
12 SSRF 三道关卡（协议/内网段与元数据地址/IP 直连禁止+解析二次校验，生产叠加域名白名单）+「新外部 MCP 接入」按放宽红线走人审。
