## 1. 总体策略

**先止血、再补地基、后长肉。** 本项目当前是"演示有效、生产无效"的原型（评估报告执行摘要判定：Demo-Grade Prototype），问题不在功能不够多——350 个端点、33 个 Agent 的外壳已经足够大——而在**地基不实**：建库链路断裂（C-01）、业务数据 100% 内存态重启全丢（E-01/E-02）、薪酬明文越权（D-01）、LLM 成本永动机（B-01）。因此本路线图**不做功能清单扩张**，目标终态只有一个：**一个真实可持久化、可重复部署、敏感数据有权限边界的 ERP MVP**——即"少 100 个端点、每个端点都真"取代"424 个 operation 中 87% 是内存假数据外壳"（E-02）。所有阶段任务的优先级排序原则：先消除"正在持续产生损害"的问题（成本、安全），再修复"一票否决部署"的问题（建库），最后才做"提升真实度"的问题（Agent 持久化、编排、RAG）。

## 2. 三阶段路线图

### Phase 1 — 止血与地基（约 3～4 人周）

**目标**：让系统"烧不到钱、泄不了密、能在全新环境一键建出来"。本阶段不碰 Agent 业务逻辑，只做四类事：掐断 LLM 空转、封死薪酬越权、修复建库链路、清除种子安全隐患。

**退出标准（全部可验证）**：
1. 全新 Docker 环境（无 erp_db 数据卷）执行一条命令后，系统启动成功，`/health` healthy，且 **35 张表全部存在**（不是静默降级到内存模式——验收时须检查 `try/except → degraded=memory`路径未被触发，见评估报告 C-01"表面 healthy、实际零持久化"的描述）；
2. 将 LLM 置于 402 欠费状态运行 1 小时：**0 次出站 LLM 请求**（对照评估报告 B-01 量化基线"3,600 次失败请求/小时"）；
3. 以非薪酬权限的普通登录用户请求 `GET /payroll/structure/{employee_id}`（`app/api/routes/hr.py:679-688`）：返回 403；
4. 已有存量 erp_db 数据的环境升级启动：数据完好、启动无报错（验证迁移路径兼容性）。

## 3. P0 四项专项方案细化

### 3.1 建库链路（C-01，评估报告称"三条建表路径全部失效"）

**背景事实**（全部来自评估报告）：alembic 唯一迁移 `upgrade()` 为 `pass`；`app/core/migrations.py` 仅建 4 张系统表且只被事件库/审计库为自己调用；`infra/docker/init-db.sql` 是 5 张对不上 ORM 的旧表；全仓库 `create_all` 0 命中；当前 35 张表源自"历史上某次已丢失的手工操作"。

**三个候选方案与取舍**：

| 方案 | 内容 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A：仅 create_all | 启动时 `Base.metadata.create_all` | 改动最小，当天可完成 | 无版本化，后续 schema 变更无出口（会重演 C-03 双轨制）；对已存在的旧表不做结构对齐 | 不单独采用，作兜底 |
| B：仅 alembic autogenerate 基线 | 以 `app/db/models.py` 为唯一事实源，autogenerate 生成基线迁移 | 正规、可版本化 | 首次配置 autogenerate 需人工核对 diff（对存量 35 张表结构可能有漂移）；全新库外的存量环境升级要写显式步骤 | 核心方案 |
| C：组合（推荐） | **models.py 唯一事实源 + alembic 真实基线迁移为主路径 + 启动期 create_all 兜底（仅全新空库时生效）** | 兼得可复现与可版本化；兜底保证"一条命令部署"永远成功 | 需要明确优先级逻辑避免兜底与迁移打架（空库判定：无 alembic_version 表则先 create_all 再 stamp head） | **采用** |

**实施要点**：
1. `alembic revision --autogenerate` 生成基线，人工逐表核对与存量 erp_db 的 35 张表一致性（存量环境 `alembic stamp head` 后纳入版本管理）；
2. `init-db.sql` 废弃或重写为仅保留 docker 初始化所需的最小内容，消除与 ORM 对不上的 5 张旧表；
3. 处理 lifespan 中 `main.py:362` 与 `main.py:416` 的重复 init_db 调用（问题总表 #20）；
4. 长期约定：**今后一切 schema 变更只走 alembic**，`migrations.py` 的 4 张系统表并入基线后退役其建表职责（化解 C-03 双轨制）。

### 3.2 Agent 持久化（E-01/E-02/C-02）

**架构方向：repository 层下沉，而非让 33 个 Agent 各自直连 DB。**
- 依据：评估报告显示全仓库 `app/agents/**` 中 DB 相关引用 0 命中（E-01），而系统内已有成熟持久化范本——`routes/messaging.py` 直接 AsyncSession（≈30 op）、`rbac_engine` 的 MySQL+缓存双轨。Agent 层保持"纯业务逻辑 + 状态读写经 repository"的结构，避免 33 个 Agent 各写一套 session 管理。
- **分批迁移策略（按价值排序，不按代码量）**：
  - 批次一（Phase 2 前半）：**payroll/hr + sales**。理由：薪酬是 D-01 越权的最高敏数据，只有落库才能实施行级隔离（D-02）；销售客户是 ERP 最高频业务单据；
  - 批次二（Phase 2 后半）：**treasury + contract**。理由：treasury 落库后 `get_payment_schedule`（`treasury/agent.py:609-613`）等接口的数据真实化，且与 B-01 治理后的预测结果缓存天然衔接；contract 有 822 行真实审批逻辑（E-05），转真投入产出比高；
  - 批次三+（Phase 3）：其余 Agent 按同模式推进，project/esg/bi 等 `_seed_data` 重灾区顺带完成假数据下沉（C-02）。
- **迁移方式**：读路径"DB 优先、内存兜底"，写路径"内存更新 + DB 落库"双写过渡，每批次稳定后再移除内存态。这样任何一批迁移出问题可单独回退，不影响其他 Agent。
- **验证**：每批次配"重启一致性"集成测试（重启前后 API 返回一致）。

### 3.3 薪酬权限修复（D-01/D-02）

分两步，Phase 1 止血、Phase 2 纵深：

**Phase 1 最小止血**（不动数据层）：
1. `GET /payroll/structure/{employee_id}`（`routes/hr.py:679-688`）依赖从 `get_current_user` 升级为 `require_permission("payroll", "read")`——直接复用同文件 `:694` 写接口的现有权限模式，不引入新机制；
2. 返回体 `bank_account` 强制脱敏为尾 4 位（对照 `payroll/agent.py:236-246` 的明文返回与 `:473-500` 的种子银行卡号）；`base_salary` 等薪酬字段按角色分级脱敏。

**Phase 2 纵深**（依赖批次一落库）：
3. 行级过滤：在 repository 查询层加 owner/department 过滤，承接 D-02——授权引擎目前仅有安全许可等级矩阵（`authorization.py:137-151`），路由级 RBAC + 行级过滤形成两层边界；
4. 将薪酬读写操作纳入审计（与 2.7 审计补全合并实施），补上 D-05 指出的"薪酬写入 0 审计"缺口。

### 3.4 LLM 调度治理（B-01/B-02/B-03 关联）

病灶在 Agent 层而非客户端层（评估报告第 4 节结论 1）：客户端令牌桶与 4xx 不重试设计合理，问题在 `base.py` 1s/tick + `llm_analyze` 吞异常不喂熔断器（`base.py:844-853`）。三层治理：

1. **降频（消灭调用源头）**：`treasury/agent.py:594-607` 的 on_tick 无条件 LLM 预测改为事件驱动（现金流变动/到账事件触发）或小时级定时；`base.py:283-320` 的 tick 周期本身可保留，改的是 on_tick 内的 LLM 触发条件。报告已指出 `treasury.py:460-468` 的规则降级预测"完全够用"，规则计算可以留在 tick 内高频跑；
2. **熔断冷却（消灭失败空转）**：`llm_analyze` 失败计数连续 N 次后触发 agent 级 LLM 冷却开关（建议 10 分钟），并调用 `circuit_breaker.record_failure()` 使现有熔断器真正参与决策；冷却期内直接走规则降级路径；
3. **结果缓存（消灭重复计算与事件膨胀）**：7 天现金流预测结果按天缓存（TTL），命中缓存不重算、不重复 `_publish_event(CASH_FLOW_FORECAST_COMPLETED)`（`treasury.py:594-607`），直接缓解 B-02"无 TTL 缓存"与 B-03"8.6 万行/天事件膨胀"；
4. **度量挂钩**：冷却与缓存命中率打日志，为成功度量指标"LLM 空转调用 0 次/天"提供验证依据。

## 5. 风险与回滚

### Phase 1

| 风险 | 说明 | 应对与回滚 |
|------|------|-----------|
| 存量 erp_db 数据与新基线迁移冲突 | 35 张表源自已丢失的手工操作（C-01），autogenerate diff 可能与存量结构有漂移；错误的迁移可能损坏现有 RBAC/消息数据 | 迁移前全量备份 erp_db；先在备份库上演练 `alembic upgrade head`；漂移处人工核对而非强行 alter；存量环境用 `stamp head` 纳管而非重建 |
| 兜底 create_all 与迁移互相打架 | 空库误判导致 create_all 覆盖或 alembic_version 状态混乱 | 明确判定顺序：检测到 `alembic_version` 表→走迁移；空库→create_all+stamp；两者均不满足→启动失败并显式报错（禁止静默降级） |

### Phase 2

|------|------|-----------|
